# Как запускать проект на sui

Этот файл читают первым. Он решает, как поднять процесс. Карта узла: `docs/architecture.md`. Каркас и пример Compose: `docs/new-service.md`. Команды на живом узле: `docs/work.md`. Состав: `docs/services.md`. Проверки и выкладка: `docs/standard.md`.

Узел `sui.example.com`. Один клон `/home/sui/sui-host`. Сервисы лежат папками `monitoring`, `chat`, `commands`, `avtobot`, у каждой свой Compose и свой юнит. Живой чат пока запускается из `/home/sui/tailnet-messenger`: его папка в репозитории есть, выкладка его не поднимает. Службы идут от пользователя `sui`. Секреты, пароли, токены и пароль `sudo` в git, в ответ и в память не попадают.

## Закон

Каждый сервис живёт в своей папке этого репозитория и в своём проекте Docker Compose. На узле папка сервиса — `/home/sui/sui-host/<имя>`. Имя Compose совпадает с именем папки. Рабочий процесс находится внутри контейнера. Чужой сервис в чужой compose не вписывают. Сеть `chat_data` новому сервису не отдают.

Проект запущен, когда совпали все пункты.

1. Свой `compose.yml` с полем `name`. Имя проекта совпадает с именем каталога.
2. Образ записан тегом. Тега `latest` нет.
3. У долгого сервиса стоит каркас из `docs/new-service.md`.
4. Сервис подключён к сети `monitoring` (`external: true`, `name: monitoring`). Сеть `chat_data` новому проекту не отдают.
5. Порт на хост, если он нужен, опубликован как `127.0.0.1:хост:контейнер`.
6. Человек открывает сервис по имени `https://sui.example.com...` через Tailscale Serve. Если страницы нет, в этой строке пишут «порта на хост нет», а код ответа берут у health внутри сети `monitoring`.
7. Поднятие и остановка идут командой `docker compose` из каталога проекта. Юнит systemd вызывает только `docker compose up -d` и `docker compose stop`. Форма юнита: `systemd/monitoring.service`.
8. В ответе есть `docker compose ps` и код ответа по тому адресу, который получит человек. У сервиса без страницы это код health.

Пока пункта не хватает, процесс на узле не оставляют.

Один уже запущенный сервис обновляют из каталога его проекта:

```bash
docker compose up --no-deps -d <сервис>
```

Свой проект останавливают командой `docker compose stop` в его папке. `docker compose down` удаляет контейнеры. В папках сервисов её не вызывают.

`git push` сам файлы на узел не выкладывает. На узел уходят названные файлы через `rsync` по SSH.

## Так проект не запускают

- Постоянный процесс из рантайма на хосте: `python`, `node`, `npm`, `uvicorn`, `gunicorn`, `java`.
- `nohup`, `screen`, `tmux`, фоновый `&`, cron на саму программу.
- Юнит, у которого `ExecStart` указывает на бинарь, скрипт или интерпретатор.
- `docker run` и `docker start`, после которых контейнер остаётся сервисом.
- `network_mode: host`, `privileged` у прикладного сервиса, порт на `0.0.0.0` или `192.0.2.15`, порт `8448`.
- Общий контейнер на несколько проектов и установка пакетов в Ubuntu ради одного приложения.

Запуск на узле один. Его делает юнит проекта: из каталога вызывается `docker compose up -d`. Вручную допустима только эта команда из того же каталога. Интерпретатор, скрипт проекта, `selftest`, проверка, которая создаёт пользователя, `docker run` и второй юнит на тот же токен процесс не запускают.

Процессы, которые уже живут вне контейнера, перечислены в `docs/services.md`. Новым проектом их форму не повторяют. В контейнер их переносят только когда задача прямо об этом просит.

Команды, которые гасят чат или мониторинг, собраны в `docs/work.md`. Ради нового проекта их не выполняют.

## Сначала четыре строки

Перед `docker compose up` на узле в ответе пишут:

- каталог и имя проекта Compose;
- образ с тегом;
- порт на `127.0.0.1` и URL `https://sui.example.com...`;
- метки `monitoring.*`, включая `monitoring.project` равный имени Compose, либо фразу «меток нет, сервису нечего проверять». Одинаковый сервис в другом проекте — отдельная цель.

Нет значения для строки — процесс на узле не стартует. Вопрос задают до запуска.

## Готово

В ответе есть четыре факта.

- `docker compose ps` этого проекта: сервис в состоянии Up. Если задан healthcheck, он healthy.
- Запрос по имени `sui.example.com` и код ответа.
- Для сервиса с `monitoring.probe` или `monitoring.metrics.port`: цель подхватил discover. Отдельный дашборд не создавался.
- `chat-synapse-1` и `monitoring-grafana-1` ради этого запуска не пересоздавались.
